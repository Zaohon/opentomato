# AI-HEMS 差距分析与演进路线 (Gap Analysis)

## 1. 当前状态 (As-Is)
目前的 AI-HEMS 是一个 **MVP (最小可行性产品)** 原型，具备以下特征：
- **核心能力**：实现了 "用户指令 -> LLM 推理 -> Python 函数调用" 的完整闭环。
- **架构**：单机 Python 脚本，包含模拟器 (Simulator)、市场服务 (Market Service) 和 LLM 桥接层。
- **数据**：**全内存 (In-Memory)**。所有状态（电池电量、策略配置、历史对话）保存在 Python 变量中，进程重启即丢失。
- **控制**：开环控制。Agent 下发策略后，缺乏持续的闭环执行机构。

## 2. 差距分析 (Gap Analysis) - 距离企业级 SaaS 的鸿沟

### 2.1 记忆与上下文 (Memory & Context) - 🔴 严重缺失
- **现状**：Agent "失忆"。无法记住用户的历史习惯（如"周五回家"）、家庭配置（"我有2辆车"）或过去的指令。
- **目标**：引入 **RAG (检索增强生成)** 和 **向量数据库**。
- **价值**：实现"千人千面"的个性化服务，而非通用的问答机器。

### 2.2 数据持久化 (Data Persistence) - 🔴 严重缺失
- **现状**：无数据库。无法生成历史账单，无法分析由于策略优化带来的节省金额。
- **目标**：
    - **时序数据 (Telemetry)**：存储设备每分钟的电压/电流/功率 (InfluxDB/TimescaleDB)。
    - **关系数据 (Relational)**：存储用户配置、策略记录 (PostgreSQL/SQLite)。
- **价值**：数据是能源管理的核心资产，也是训练未来私有模型的燃料。

### 2.3 复杂任务编排 (Agent Orchestration) - 🟡 部分缺失
- **现状**：单步 ReAct。只能处理"一问一答"。
- **目标**：引入 **LangGraph** 或 **状态机**。处理跨时间周期的任务（如"明早8点前充满"涉及未来12小时的多次调度）。
- **价值**：处理现实世界中复杂的、非瞬时的能源任务。

### 2.4 安全护栏 (Safety Guardrails) - 🔴 潜在风险
- **现状**：LLM 输出直接通过工具执行。存在幻觉导致参数错误的风险。
- **目标**：在 Agent 与设备之间增加 **确定性校验层 (Deterministic Validation Layer)**。
- **价值**：确保物理设备安全，防止过充过放或参数越界。

## 3. 演进路线建议 (Roadmap)

我们采取 **"纵向深挖"** 策略，优先构建数据底层。

- **Phase 1: MVP Shell** (✅ 已完成)
- **Phase 2: 数据持久化层 (Data Layer)** (✅ 已完成)
    - 引入 MySQL (阿里云 RDS)，实现用户设备绑定关系管理。
    - 引入 InfluxDB (阿里云 TSDB)，实现秒级遥测数据存储。
    - 引入 MQTT (阿里云 IoT)，实现指令下发闭环。
    - 建立 `strategy_logs` 审计日志，确保操作可追溯。
- **Phase 3: 企业级记忆增强 (Memory & RAG)** (🟡 部分完成)
    - **技术栈**: **DashVector (阿里云原生 SDK)** + **DashScope Embeddings** (已移除 LlamaIndex 以提升兼容性与性能)。
    - **核心能力状态**:
        - ✅ **User Profile Memory**: 记住非结构化偏好（"周五回家"、"价格敏感"）。
        - 🔴 **Knowledge Base**: 检索设备说明书/故障代码库（**尚未实现**）。
- **Phase 4: 服务化与高可用 (Service Mesh)** (✅ 已完成)
    - FastAPI 微服务改造，支持 K8s 部署。
    - Celery 异步任务队列。
