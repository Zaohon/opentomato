# AI Agent 驱动的家庭能源管理系统 (AI-HEMS) 架构设计方案

## 0. 核心愿景
打造一个"懂能源、懂用户、懂经济"的专属家庭能源管家。从被动的设备监控，转变为主动的能源策略优化与生活方式服务。

## 1. 关键决策与工程约束 (Confirmed)
在此前讨论中，我们明确了以下核心技术路线，作为后续开发的基础：

1.  **设备模型**：**统一硬件**。采用"光储充五合一"一体机（电网 Grid、负载 Load、电动车 EV、光伏 PV、电池 Battery）。无需考虑异构设备兼容性，大大简化了数据清洗层。
2.  **数据上报策略**：**按需/变化上报 (Report on Change)**。
    *   仅在状态变更（如插枪/拔枪）、功率变化 >5%、SoC 变化 >1% 或故障发生时上报。
    *   大幅降低 1 万用户的云端并发压力和流量成本。
3.  **闭环反馈**：**开环控制**。Agent 下发策略后视为任务完成，**不进行**主动的执行监控和纠错（由底层固件负责基本重试）。
4.  **离线安全策略**：**本地安全模式 (Local Safe Mode)**。
    *   设备端内置"看门狗"。若检测到云端 MQTT 心跳丢失 > 5分钟，自动切换至"自发自用"模式（光伏优先供负载，余电存电池，不从电网取电，确保不产生意外电费）。

## 2. 系统总体架构 (分层设计) - 针对秒级响应优化的双回路架构 - 针对秒级响应优化的双回路架构

鉴于 **完全依赖云端** 且要求 **秒级响应**，常规的 "用户 -> 大模型推理 -> 执行" 链路太慢（大模型推理通常需要 2-5 秒）。
必须采用 **快慢双回路 (Dual-Loop)** 设计：

### 2.1 极速控制回路 (Fast Loop) - 秒级响应
*   **场景**：用户直接指令（"打开充电桩"、"停止充电"、"把空调调到 26 度"）。
*   **流程**：
    1.  用户语音/文字输入。
    2.  **意图识别微服务 (NLU)**：使用微调的小模型 (BERT/DistilBERT) 或极速 LLM (Claude Haiku / GPT-3.5)，耗时 < 200ms。
    3.  **规则匹配**：识别到 `CMD_STOP_CHARGE`。
    4.  **指令下发**：直接通过 MQTT 长连接推送到设备，耗时 < 100ms。
    5.  **反馈**：前端立即显示"正在停止..."。
*   **特点**：绕过复杂推理，直达设备，确保体感上的"秒级"。

### 2.2 智能策略回路 (Slow Loop) - 分钟/小时级优化
*   **场景**：复杂任务、策略规划（"明天我要出远门"、"帮我省钱"、"现在的电价策略是什么"）。
*   **流程**：
    1.  用户输入被 NLU 识别为 `INTENT_COMPLEX_QUERY`。
    2.  **路由**：请求转发给 **AI Agent Core (Claude Sonnet/Opus)**。
    3.  **ReAct 推理**：Agent 查询记忆、查询电价、分析天气。
    4.  **策略生成**：Agent 输出高层策略对象（如 `StrategyConfig`）。
    5.  **配置下发**：将策略配置下发给云端调度算法。
    6.  **闭环执行**：云端调度算法根据策略，每分钟计算一次控制指令（SetPoint），通过 MQTT 下发给设备。
*   **特点**：深思熟虑，生成最优解，不追求毫秒级，但追求准确和个性化。

### 2.3 物理层 & 边缘计算层 (Edge) - 纯执行与安全
*   **设备**：光伏逆变器、储能电池 BMS、智能充电桩。
*   **功能**：
    *   **哑终端 (Dumb Terminal)**：只负责执行云端下发的 MQTT 指令（如 `set_power=3000W`）。
    *   **安全熔断**：本地硬编码的电气保护（过流/过压/过温保护），不依赖云端。
    *   **断网默认策略**：若 MQTT 心跳丢失 > 1分钟，自动切换到"自发自用 (Self-Consumption)"安全模式。

## 3. AI Agent 核心层 (The Brain)
这是系统的"大脑"，负责推理、记忆和交互。

#### A. 记忆系统 (Memory System) - "千人千面"的关键
为了服务 1 万用户，不能只靠 Prompt Context，必须引入 **RAG (检索增强生成)**。
- **长期记忆 (Vector DB)**：使用 Milvus/Qdrant/Pinecone。
    - *存储内容*：用户历史对话、长期的用电习惯（"用户 A 周五晚上通常会给车充满电"）、家庭配置信息。
- **短期记忆 (Redis)**：
    - *存储内容*：当前的对话上下文、当天的天气、当天的实时电价、当前电池 SoC。
- **知识库**：
    - 能源专家知识：电池寿命维护建议、分时电价策略、光伏发电原理。

#### B. 核心 Agent 工作流 (基于 ReAct/CoT)
当用户说："我明天要出远门，把车充满。"
1.  **感知 (Perception)**：
    - 获取当前 SoC (30%)。
    - 获取明天天气 (晴天)。
    - 获取当前电价 (高峰期)。
2.  **记忆检索 (Recall)**：
    - 检索用户习惯：用户定义的"出远门"通常是指 300km+，需要 100% 电量。
3.  **规划 (Planning)**：
    - *思考*：现在电价高，不宜立即充电。预测明天上午光伏发电充足。但用户明天一早出发，可能来不及用光伏。
    - *策略*：建议利用凌晨低谷电（0:00-5:00）将电量充至 100%。
4.  **行动 (Action)**：
    - 调用 `set_charging_schedule(start="00:00", target_soc=100)`。
    - 回复用户："好的，已为您安排。考虑到现在电价较高，我将在凌晨 0 点开启低谷充电，预计明早 6 点充满，比现在充能省 15 元。"

### 2.4 应用服务层 (Application)
- **App/小程序**：聊天界面、数据仪表盘。
- **语音助手集成**：Alexa/Siri/小爱同学 接口。

## 3. 针对 1 万用户的扩展性设计 (Scalability)

### 3.1 异步处理架构
1 万用户并不是同时在线对话，但设备数据是 7x24 小时上报的。
- **消息队列 (Kafka/RabbitMQ)**：将设备数据流与 AI 分析流解耦。
- **触发机制**：
    - **主动触发**：用户发消息 -> 调用 LLM。
    - **被动触发**：电价变动/电池低电量 -> 触发规则 -> (可选) 唤醒 Agent 分析 -> 推送建议。

### 3.2 Token 成本控制
直接将所有数据扔给 GPT-4/Claude 3.5 是极其昂贵的。
- **大小模型协同**：
    - **小模型 (Llama 3 8B / Mistral)**：处理意图识别、简单的闲聊、格式化数据提取。
    - **大模型 (GPT-4o / Claude 3.5 Sonnet)**：处理复杂的策略生成、疑难问题解答。
- **数据预处理**：不要把原始的秒级电压数据发给 LLM。先由传统算法聚合成"过去 1 小时平均发电量"，再传给 LLM。

## 4. 智能功能规划 (Features)

### 阶段一：智能助理 (Q&A)
- 解释账单："为什么昨天电费这么贵？"
- 设备查询："现在的电池电量能支持家里开空调多久？"
- 故障排查："逆变器亮红灯是什么意思？"

### 阶段二：智能建议 (Advisory)
- 节能提醒："检测到您家里没人但空调开着，建议关闭。"
- 策略推荐："明天是阴天，光伏发电不足，建议今晚谷电时段先把电池充满。"

### 阶段三：自主控制 (Autonomous)
- **全自动光储充协同**：Agent 自动根据天气、电价、用户习惯，每日生成最优充放电策略并执行，用户只需查看"每月为您节省了多少钱"的报告。

## 5. 开发技术栈建议

- **LLM Orchestration**: LangChain 或 LlamaIndex (处理 RAG 和 Tool Calling)。
- **Backend**: Python (FastAPI) / Go (处理高并发连接)。
- **Vector Database**: Milvus (开源、高性能，适合私有化)。
- **Agent Framework**: AutoGen 或 LangGraph (实现多 Agent 协作，例如一个负责'电价监控'，一个负责'用户交互'，一个负责'策略计算')。

## 6. 下一步行动建议
1.  定义 **Tools 列表**：明确 Agent 可以调用哪些 API (如 `get_battery_status`, `set_charge_mode`, `get_weather_forecast`)。
2.  设计 **System Prompt**：确立 Agent 的人设（专业的、节能的、贴心的）。
3.  搭建 **MVP 原型**：跑通 [用户输入 -> 意图识别 -> 读取模拟设备数据 -> 生成策略 -> 返回文本] 的闭环。
